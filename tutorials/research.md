# 怎样从风控人员角度做研究

## 先确定平台的判断问题

将来源按问题分类：服务范围与资格、账号完整性、支付风险、滥用行为、资源公平、
账号被盗和异常访问。它们是研究分类，不代表已经确认 上游服务商 使用某个模型。
注册阶段与长期使用阶段分开；不要用一次反滥用报告解释所有注册失败。

每个问题记录：平台希望降低什么损失、判断哪个实体、在哪个事件时点、可能采取何种措施。
例如，“服务范围”需要真实地区与主体资格，而非仅看 IP 数据库；“客户端是否安装”只解释工具可用性。

## 写一个能被反驳的特征主张

使用 [特征卡](../templates/feature-card.md)。每张卡至少包括：

- 原始公开来源、版本、核对日与生效日。
- 用户可见读数，以及平台可能看到但我们看不到的部分。
- 支持证据、反对证据与正常反例。
- 一个可复现测量方法，以及无法推导的结论。

“中文环境导致封号”包含大量混杂因素，单凭语言和一个被封帖子无法成立。
可执行的研究问题可以是“语言设置是否影响某项页面能力”，其结果仍不能升级为封禁规则。

## 让 Graph 回答具体问题

当前证据图为 `source → claim → rule ← check`，特征连接到主张，
每个主张保留范围、状态、反驳条件。用 `zhibi theory --format json` 导出节点和边，
用 `zhibi explain network.route` 查看具体规则关系。

来源带时间和有效期。后续的事件轨迹、支持/反驳材料及替代关系需要独立验证。
同一个出口不能直接合并成一个人；本地观测不能补出平台全局账户关系。

## 验证与写回规则

先在合成场景检验测量语义和正常反例，再在自愿用户的真实环境检验可用性。
记录缺失、失败、撤回、失访和观察窗口。账号成效研究需要独立设计、充分样本及混杂因素处理。
不要用批量注册或诱发封禁制造标签。

规则修改需要：明确适用范围、可追溯来源、失败处理、正常反例和回归测试。
第三方网站或帖子只能作为资料，不可作为可执行表达式载入。

## 三个已有账号案例怎样写

作者于 2026 年 10 月 18 日自述已开通并稳定使用三个 20x Max 账号。
具体过程、注册日期、使用时长与逐账号观察记录尚未提供。
分别使用 [案例模板](../templates/case-study.md) 记录；未知字段留空。
教程可按“当时遇到的问题 → 我掌握的证据 → 做过什么 → 观察到什么 → 还有哪些替代解释”展开。
不要补写未发生的操作或把三次经验换算成防封效果。
