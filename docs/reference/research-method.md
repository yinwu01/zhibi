# 风控研究方法

研究最终服务于注册准备与异常处理。每个候选特征都要回答：它改变了用户的哪条决策，这个改变由什么证据支持？

## 从平台目标开始

先区分访问资格、账号安全、支付风险、协同滥用、反蒸馏和服务可用性，再明确产品、业务阶段与判断对象。这些类别是研究框架；只有原始资料明确披露的机制，才能在对应范围内作为已知事实。

注册、登录、支付、请求限流、内容拒绝与账号暂停采用不同结果标签。某类技术报告的新发现不能自动迁移成注册拦截条件。

## 证据与主张分开

| 类型 | 可支持什么 | 不可直接推出什么 |
| --- | --- | --- |
| 官方政策 | 原文范围内的资格与要求 | 未披露的内部实现和权重 |
| 官方技术披露 | 披露场景中的机制或观测 | 所有产品和业务阶段均适用 |
| 可复现测量和代码审查 | 具体版本采集、计算或修改了什么 | 服务端如何使用该字段 |
| 第三方情报 | 供应商给出的分类或历史记录 | 目标服务 内部判定 |
| 有观察窗口的队列 | 指定人群和条件下的关联 | 没有控制混杂的因果关系 |
| 个案、帖子和教程 | 提供线索与候选解释 | 普遍成功率、阈值或确定规则 |

来源登记包含 URL、作者、发布日期、查阅日期、版本或提交、适用范围与简短摘要。转述共同上游不能算多份独立证据。每个 claim 只表达一个可核验主张，并记录支持与反驳材料。

## 特征研究卡

使用 [feature-card.md](../../templates/feature-card.md)，记录平台动机、对象、原始信号、派生特征、可见范围、时间窗口、数据来源、正常反例、验证方式、行动价值和复核条件。

例如“浏览器与 CLI 出口不同”：

- 测量命题：两个明确客户端在可比条件下得到不同出口。
- 正常反例：用户有意分流、地址族不同、测试时间不同。
- 可行动建议：确认路由是否符合预期；发现具体故障后处理并复验。
- 未获支持的扩展：因此会封号，或改为相同出口就不会封号。

## Graph 的验证价值

本地实体事件图用来比较自己已记录的入口、配置和时间关系；证据图用来回答建议从何而来、哪条新资料影响旧规则。每条边保留来源与时间。不确定的关联保持不确定，不能依靠图形展示掩盖缺失数据。

## 规则进入产品的条件

规则至少应当有适用范围、必要观测、证据引用、正常反例、复核日期及可执行的下一步。研究状态为 `proposed` 的主张可展示为研究问题，不能产生确定性的封禁判断。

“supported”需要限定支持的具体命题。配置比较规则即使经过测试，也只能支持配置判断。模型可以提出新假设，但不能在一次用户检查中临时将假设升级成启用规则。

## 统一审查检测工具

记录工具版本和实际操作范围，逐项核对：

1. 采集了哪些字段，在哪个观测对象和路径采集？
2. 输入如何变成分数，权重与阈值来自哪里？
3. “风险分”对应的目标变量、分母与观察窗口是什么？
4. 哪些正常使用情形也会被判异常？
5. 超时、缺失、过期资料、供应商冲突会怎样处理？
6. 数据发给谁，建议涉及哪些服务和商业关系？
7. 修复验证的是配置生效，还是另有账号结果证据？

结论按“已复现、文档自述、推断、未检查”标注。用相同问题审查本项目，不把未检查写成不存在，也不把没有证据写成已证明无效。

## 案例与效果验证

以作者自述已开通并稳定使用的三个 20x Max 账号作为复盘起点（2026 年 10 月 18 日补充），具体过程和使用时长待提供。使用 [case-study.md](../../templates/case-study.md) 收集用户授权的最少必要信息，保留失败、正常反例、观察截止时间和失访。

先评估测量是否正确、错误分流是否准确、建议是否可执行、是否减少无效操作。账号结果需有分母、时间窗口和混杂因素说明；模拟测试通过率不是防封成功率。受控网络实验只能验证采集与路由，不模拟平台的未知处分模型。
