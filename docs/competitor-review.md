## 这次实际采用与独立审查的部分

| 来源 | 实际采用 | 单独审查的判断 |
| --- | --- | --- |
| CCBaga `browser-network.ts` | IP 验证、浏览器自身出口请求和相关测试 | 端点匹配只证明那次请求；知彼将失败、地址族、时间与自动化上下文单列 |
| CheckCC `client-engine.ts` | 当前浏览器环境采集 | 地区画像加权模型没有作为 目标服务 已证实规则引入；语言/时区留作背景事实 |

这使比较落到具体代码行为：既保留成熟实现，也单独验证从观测到建议的推导。

## CC Baga

[CCBaga README](https://github.com/liseami/CCBaga) 描述了桌面环境管理、本地身份归档、独立浏览器实测、系统配置及可选网络 Skill。文档明确绿色检查描述观测匹配，不能保证账户被接受；网络模块是可选的。

值得学习的是：操作前检查、实际测量、保存与恢复、把配置变更和结果验证分开。

我们要进一步审查的是：某个配置目标依据是什么；哪些正常场景不满足该目标；从“配置匹配”到“账号结果改善”是否有独立证据；额外网络设施带来多少费用、凭据暴露面与维护工作。没有成效证据时，只能保留未知，不能反向断言其无效。

项目取舍：第一版观察用户实际浏览器，优先诊断具体问题；额外浏览器、指纹轮换、环境清理与网络重构不作为默认注册准备步骤。用户确有配置故障时，建议需说明原因并能够复验。

## CheckCC

[CheckCC README](https://github.com/yacuo/check-cc) 描述了浏览器与运行环境采样、一致性提示、IP 相关信息和注册前后的风险提示，并声明不读取 目标服务 Cookies、不默认上传检测结果。

值得学习的是：低门槛采集、分项解释、示例报告和自部署入口。不能把“不读取 Cookies”当作本项目独有能力，也不能无依据指控其窃取资料。

我们要进一步审查的是：每项采样的含义、权重依据、缺失数据处理、地区画像与账号风险之间的推导，以及页面版本和开源仓库版本是否一致。显示百分比不代表完成了概率校准；是否存在验证数据应查证后记录。

项目取舍：第一版显示采集状态、依据与行动项，不生成未经验证的综合封号概率。对时区、语言和地区差异保留正常解释。

## 检测网站与指南的共同审查

网站或指南是信息入口，不能仅凭形式判断质量。我们批判的是具体做法：未经支持的确定性结论、缺乏说明的数据采集、把技术匹配等同账号安全，以及没有论证的采购建议。

商业推广应披露，但推广关系本身不证明技术错误。部分工具本来就有本地处理、隐私说明和边界声明，应在比较时承认这些能力。

## 我们选择证明的差异

| 设计目标 | 发布时应提供的证明 |
| --- | --- |
| 从平台动机研究 | 风险分类、判断对象、特征卡和适用范围 |
| 从事实追到建议 | `check_id → observation_id → rule_id → evidence_id` 及报告 |
| 正确处理未知 | 全失败、部分缺失、过期资料、冲突来源的验收结果 |
| 避免误导正常用户 | 多语言、旅行、企业出口和有意分流的正常反例 |
| 隐私可检查 | 字段白名单、外部请求清单、摘要和导出检查 |
| 建议可以复查 | 具体问题、动作、前后观测与后续结果 |

这些设计要求已部分落实为本地 alpha 的规则、测试与报告，但尚未由公开发布和真实用户结果验证。市场上是否已有完整相同方案仍需持续比较，因此首页不宣称“首个”或“唯一”。
